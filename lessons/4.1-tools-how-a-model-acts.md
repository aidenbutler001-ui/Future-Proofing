## Read
So far a model only produces text. A **tool** lets it do more: search the web, read a file, run code, look up an order. Here is the whole mechanism:

1. The program tells the model which tools exist. Each tool has a **name**, a **description** and a list of **inputs** (its schema).
2. The model reads your request. Instead of answering, it may reply with a request: "call `get_weather` with city = Oslo".
3. **The model does not run anything.** The surrounding program (the harness, covered in Module 5) runs the function.
4. The result goes back into the context. The model reads it and writes the final answer, or asks for another tool.

Because the model chooses tools by reading their descriptions, **the description is a prompt**. A vague description gets the wrong tool picked, or the right tool called with the wrong inputs.

Good tool descriptions say what it does, when to use it (and when not to), and what each input means, with an example.

## Example
Two tools: `search_orders(customer_email)` and `search_products(keyword)`. A user asks "Where is my order?" A description like "Searches things" makes the model guess. "Finds a customer's past orders and their shipping status. Use when the customer asks about an existing order." makes the right choice obvious.

**Opsec check.** A tool is a new way for data to leave. Before adding one, ask what it can read, what it can send, and where it sends it (lessons 0.1 and 4.0).

## Puzzle: Write the tool description
You get three tools with blank descriptions and 8 user requests. Write a description for each so a simulated model picks the right tool and fills in valid inputs.
- Goal: 7 of 8 requests routed correctly.
- Hidden tests: the 8 requests, including two that need no tool and one that needs a tool with a missing input (the model should ask).
- Grader: rules compare the chosen tool and inputs to the key; feedback quotes the line of your description that misled the model.

## Hints

2. Say when *not* to use each tool.
