## Read
Models vary and services go down, so automations need guardrails. Design each step to answer four questions:

1. **What does a bad output look like, and how do we detect it?** Validate: is the JSON valid, is the date a date, is the amount within range?
2. **What happens on failure?** Retry (with a limit), fall back to a simpler path, or stop and alert a person.
3. **Can running it twice cause harm?** Make steps **idempotent** where you can: running again doesn't send a second email or create a duplicate record. Use an ID to check "did I already do this?"
4. **Where does a human look?** For anything costly, irreversible or uncertain, route to a person with the context they need to decide quickly.

Also: **log** inputs, outputs and decisions so you can reconstruct what happened, and set **limits** on spend and run count so a bug can't run up a bill.

Aim for failing loudly and safely. A silent wrong result is worse than a visible stop.

**Opsec check.** Error messages, logs and retries can copy sensitive data into places with weaker protection. Redact logs, restrict who can read them, and set how long they are kept.

## Puzzle: Make it survive
A working invoice pipeline fails under 5 stress cases: the model returns text instead of JSON, the email service times out, the same invoice arrives twice, an invoice total is 100 times usual, and a scanned image is unreadable. You add validation, retries, de-duplication and human review rules.
- Goal: all 5 cases end safely (correct result or a clear human handoff) with no duplicates and no more than 3 retries.
- Hidden tests: the 5 cases plus 3 further ones you aren't shown.
- Grader: simulator and rules; feedback names the unprotected step.
