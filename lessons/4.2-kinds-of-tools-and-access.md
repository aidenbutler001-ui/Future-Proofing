## Read
Common kinds of tools:

| Kind | What it does | Main risk |
|---|---|---|
| **Search / retrieval** | Finds fresh or private information | Bad or untrusted sources |
| **Code execution** | Runs code to calculate, analyze, make charts | Wrong code, using resources |
| **File access** | Reads, creates, edits files | Overwriting or leaking files |
| **Calling other software (APIs)** | Sends email, edits a calendar, updates a database | Real-world side effects |
| **Browsing / computer use** | Clicks and types in a browser or app | Mistakes at speed, hidden instructions on pages |

Two ideas to hold on to:
- **Read vs. write.** Tools that only look are safer than tools that change things. Start with read-only.
- **Least privilege.** Give a tool the narrowest access that gets the job done: one folder, not the whole disk; draft emails, not send them.

Standards are emerging so that one tool can plug into many AI products. The best known is the **Model Context Protocol (MCP)**, an open standard for exposing tools and data to models.

**Opsec check.** Default to read-only and one folder, never a whole drive or mailbox. If the machine holds confidential files, run tools in a separate environment (lesson 4.0).

## Puzzle: Pick the tools, set the limits
You get 4 jobs (e.g. "answer questions about our policy PDFs", "tidy my downloads folder", "reply to customer emails"). For each, choose tools from a list and set their access (read-only, write, ask first).
- Goal: each job has what it needs and no more.
- Hidden tests: 4 jobs with one trap each (a write tool where read-only would do; a job that needs a human check before sending).
- Grader: answer key with allowed ranges; feedback names the extra access and what could go wrong.
